# Architecture Decision Framework

## 1. 先核对事实

每次设计或开发前：

1. 检查 `git status --short`。
2. 检查实际文件、package scripts、依赖和测试。
3. 区分当前实现、未提交改动、规划文档和未来设想。
4. 不因为目录名或规划文字假设功能已经存在。

## 2. 抽象准入条件

只有满足至少一项才新增长期抽象：

- 已有两个独立实现。
- 已有两个独立消费者。
- 当前实现已经出现可复现的替换需求。
- 领域边界需要稳定契约才能避免循环依赖。
- 安全边界明确要求隔离。

否则优先使用简单的显式接口或应用服务。

## 3. 新能力的状态标记

每项设计必须注明：

- 已实现
- 部分实现
- 设计中
- 未来规划
- 暂缓
- 存在问题

架构文档不能把目标架构写成当前能力。

## 4. 复杂技术的门槛

引入 SQLite、WASM、CRDT、Agent、Pipeline、远程 Plugin 或新的 Adapter 前，必须有：

- 明确用户场景。
- 当前方案的可复现失败证据。
- 迁移和回退方案。
- 测试和性能验收标准。
- 对 Stable Contract 的影响说明。

## 5. 交付检查

代码变更完成后至少运行：

```bash
corepack pnpm typecheck
corepack pnpm build
git diff --check
```

涉及浏览器能力时，另行记录真实浏览器验证，不用 Node 构建成功替代浏览器验收。
